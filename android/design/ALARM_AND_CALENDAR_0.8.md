# 0.8 알람 화면과 선호 캘린더·알람 앱 연동

상태: Astra 설계를 기준으로 GPT-5.5 구현과 Astra 소스 검토를 완료했다. 최종 테스트와 남은 실기기 검증은 `VERIFICATION_0.8.md`를 따른다. 아래 본문은 구현 전 요구와 검증 기준을 기록한다.
순서: Astra 설계 → GPT-5.5 구현·검증 → Astra 독립 검토. 휴대폰이 오프라인인 동안 실기기 연동 성공을 주장하지 않는다.
목표: 엄마의 명확한 일정 저장 요청은 선택한 목적지에 실행하고 결과를 증명한다. 울리는 화면은 지금 할 행동과 소리 제어를 빠르게 찾도록 만든다.
범위: Android 기본 API와 기존 의존성만 사용. OCR 의존성·등하교 서비스 추가·생성 AI 연결은 이 단계 밖이다.

## 1. Alarmy 참조와 모모의 설계 판단

화면 근거는 상위 작업에서 직접 확인한 [Alarmy 공식 Google Play 이미지](https://play.google.com/store/apps/details?id=droom.sleepIfUCan)다. 소개용 스크린샷이며 실제 설치 앱의 측정 결과가 아니다.
첫 등록 이미지는 기본 알람의 여러 시각과 알라미의 단일 알람을 비교하는 소개 그림이다. 07:00/07:05 목록은 '기본 알람' 쪽이므로 실제 알라미 목록 화면의 증거로 사용하지 않는다. 두 번째 미션 소개 화면은 어두운 남색 바탕, 흰 과제 제목, 가운데 단일 과제, 큰 붉은색/분홍색 확인 대상으로 주의를 모은다.
세 번째 이미지는 영상 배경 선택 gallery다. 실제 울리는 화면을 실측한 자료가 아니므로 모모의 영상 배경·기상 미션 요구사항으로 확대하지 않는다.
관찰에서 취할 원칙은 큰 시각·한 가지 활성 행동·눈에 잘 보이는 제어다. 모모는 Clay의 따뜻함을 작은 강조에만 사용하고 알람 전체에 무거운 장식을 두지 않는다.
[공식 기능 소개](https://alar.my/en/blog/alarmy-force-wake-up-features-heavy-sleepers)의 이미지 CDN은 상위 작업 브라우저에서 차단되어 시각 근거로 사용하지 않았다. 다른 경로로 차단을 우회하지 않는다.
모모에서 비교할 항목은 시각과 행동의 우선순위, 정지·다시 알림의 구분, 잠금 상태의 개인정보, 한 손 조작과 큰 글자다.
제품 목표는 엄마가 할 일을 알아보고 원하는 제어를 쉽게 하는 것이다. Alarmy보다 낫다는 결론은 동일 과제 사용자 검증 전에는 내리지 않는다.
소리 점증·강제 미션·임의 소리 변경·전원/삭제 방해·확인될 때까지 무한 반복을 추가하지 않는다.

## 2. 울리는 화면의 정보 순서

```text
9월 20일 일요일             모모의 알림

                 07:00
                  예약 시각

          등교 가방에 물티슈 넣기
          오늘 챙길 일 1개

          [       소리 끄기       ]
          [    10분 뒤 다시 알림   ]

          내용 보기     준비 완료
```

예약 시각은 56~72sp 범위의 큰 숫자, 핵심 행동은 26~32sp를 목표로 한다. 글자 확대 시 잘림 없이 줄바꿈한다.
하단의 주 제어는 스크롤 없이 접근 가능한 56dp 이상 높이로 배치하고 중요한 버튼 사이 간격은 최소 12dp로 둔다.
밝은 단색 바탕·진한 글자 또는 검증한 어두운 테마를 사용한다. 기존 Clay 색상은 재사용하되 장식 그림자·마스코트가 행동보다 커지지 않는다.
본문 대비 4.5:1 이상을 검증 목표로 두고 TalkBack 이름·초점 순서를 날짜→시각→행동→제어로 정한다.
큰 제목이 3줄을 넘으면 핵심 3줄과 “내용 보기”를 제공한다. 전체 문장은 상세에서 접근 가능해야 한다.
여러 일이면 첫 행동과 “다른 일 2개”를 표시한다. 전체 일괄 완료 버튼을 만들지 않는다.
브리핑 화면에서는 “준비 완료”를 생략하고 “내용 보기”로 들어간다. 특정 task ID에 연결된 알림에서만 완료가 가능하다.
참고 wireframe의 예시 텍스트·요일은 레이아웃 설명용이며 실제 실행 화면은 저장된 날짜로 계산한다.

## 3. 소리·다시 알림·완료는 서로 다른 상태

`소리 끄기`는 현재 알림의 소리/TTS/진동과 화면 알림을 정지한다. 부탁 완료·일정 삭제·다음 정기 브리핑 취소를 하지 않는다.
현재 `stopAlarm()`이 `710+slot`만 취소하는 경로는 고친다. 실제 발행한 일반/미리보기/task notification ID를 검증된 occurrence에 보관해 자기 알림만 취소한다. 미리보기의 `1710+slot`과 실제 브리핑을 혼동하지 않는다.
`10분 뒤 다시 알림`은 현재 occurrence에 대해 now+10분을 실제 저장·예약한 뒤 소리를 끈다. 저장 실패면 “다시 알리지 못했어요”와 직접 소리 끄기를 제공한다.
최초 반복 선택은 10분 하나를 크게 보여주고 상세에서 5/10/30분을 선택하게 한다. 같은 발생 건당 최대 3회, 누적 최대 60분을 제품 제한으로 둔다.
자동 재시도 횟수와 사용자의 snooze 횟수는 별도다. 만료 기한을 넘는 snooze는 만료되는 시각을 알리고 다음 브리핑으로 몰래 바꾸지 않는다.
성공한 snooze에는 새 절대 시각을 표시한다. 재탭·화면 회전·중복 intent가 같은 예약을 여러 개 만들지 않도록 occurrence ID/generation을 검사한다.
`준비 완료`는 잠금 해제 후 해당 task를 완료하고 연결된 모모 예약을 취소한다. 외부 캘린더 행사 참석이나 외부 알람 삭제로 연결하지 않는다.
잠금 중에는 자녀 이름·학교·약속·장소·건수를 노출하지 않는다. “모모 알림 · 잠금을 풀면 내용을 볼 수 있어요”와 소리 끄기/다시 알림만 제공한다.
잠금 중 완료·원문 보기·개인정보 TTS는 막는다. 잠금 해제 뒤 다시 저장 상태와 동의를 확인한다.
일반 뒤로 가기·앱 전환·전원 버튼을 존중한다. 열린 화면이 종료되면 현재 모모 소리도 멈추며 완료 처리하지 않는다.
자동 소리 정지는 현재의 30초 상한을 유지한다. 권한이 없으면 상단 알림/일반 알림으로 대체하고 전체화면이 열린다고 보장하지 않는다.
소리 반복은 사용자가 고른 모모 알람 모드에 한정해 [FLAG_INSISTENT](https://developer.android.com/reference/android/app/Notification#FLAG_INSISTENT)와 30초 timeout을 함께 검토한다. 알림창 열기·정지로 반복이 끝날 수 있으며 일반 브리핑에 적용하지 않는다.
[Android 14 전체화면 제약](https://developer.android.com/about/versions/14/behavior-changes-14#secure-fsi)에 따라 실제 사용자 알람 경로와 `canUseFullScreenIntent`를 확인한다. 기상 미션 복제가 아닌 일정·챙길 일 중심의 제한된 알람 화면이다.
별도 알람 앱이 실제로 울릴 때는 그 앱의 화면이 나타난다. 모모가 Alarmy나 다른 앱의 울리는 UI를 바꾸는 기능은 아니다.

## 4. 선호 앱과 저장 계정을 구별

| 설정 | 저장하는 것 | 사용자에게 설명할 범위 |
|---|---|---|
| 일정 저장 위치 | CalendarProvider의 쓰기 가능한 calendar ID·계정/이름 | 실제 일정이 저장될 계정과 캘린더 |
| 일정 확인 앱 | 실제 지원하는 설치 앱/intent handler | 저장된 일정을 여는 선호 앱, 저장 계정과 별개 |
| 외부 입력 앱 | `ACTION_INSERT`를 실제 처리하는 선택 앱 | 입력 화면을 여는 앱, 모모에서 저장 확인 불가 |
| 알림 방식 | 모모 날짜 알림 또는 검증된 `ACTION_SET_ALARM` 처리 앱 | 특정 날짜 지원 여부가 다름 |

첫 유효 요청 시 필요한 목적지만 한 번 선택한다. 이후 명시적 사용자 저장 요청에는 같은 질문을 반복하지 않는다.
쓰기 가능한 캘린더는 READ/WRITE 권한과 접근 수준을 확인한 뒤 조회한다. 읽기 전용·제거된 계정은 선택할 수 없으며 쓰기 직전 재검증한다.
공유 캘린더라면 저장 대상 행에서 계정/캘린더명을 보여준다. 숨은 기본 계정에 임의로 쓰거나 참석자를 추가하지 않는다.
캘린더 앱에 표시되는 계정과 Android CalendarProvider가 노출하는 계정은 다를 수 있다. 네이버 등 전용 서비스의 provider 지원을 가정하지 않는다.
선호 앱 후보는 실제 intent handler 조회로 찾고 실행 직전 다시 확인한다. Alarmy packageName이나 intent 지원을 추측하지 않는다.
선택 앱 제거·비활성화·권한 철회 시 조용히 다른 외부 앱에 보내지 않는다. 가능한 목적지를 한 번 선택하게 한다.

## 5. 에이전트 요청 파싱 계약

`LocalAgentEngine`은 부작용 없는 해석만 하고 실행은 별도 coordinator가 맡는다. 대화 출력 문자열을 다시 분석해 저장하지 않는다.
결과는 기존 로컬 부탁과 별개인 typed `CalendarCreate`, `AlarmRequest`, `NeedsClarification`, `Lookup/NoMutation`으로 구분한다.
지원 입력: “2026년 10월 17일 오후 2시 치과 약속 캘린더에 저장해줘”, “10월 17일 14:30 상담 일정 추가”, “내일 오전 7시 물티슈 알람 맞춰줘”.
날짜는 명시 연도+월일, 월일, 오늘/내일/모레를 지원한다. 시간은 오전/오후 H시 [M분], HH:mm, 명확한 24시간 값을 지원한다.
오전/오후 없는 1~12시 표현은 모호성으로 묻는다. “3시”를 새벽 3시로 자동 저장하지 않는다. 00시/13~23시 또는 HH:mm은 24시간 형식으로 처리한다.
12 AM은 00시, 12 PM은 12시로 처리하고 오전/오후 범위 1~12, 분 0~59, 유효한 월일·윤년을 엄격히 검증한다.
연도 없는 월일은 현재 선택 시간대의 올해 후보를 만든다. 과거가 되면 다음 해로 넘기지 않고 날짜 확인을 요청한다.
현재 시각 이전·존재하지 않는 날짜·빠진 시작 시각이면 저장 0건이며 필요한 값만 질문한다. 캘린더 일정에는 제목이 필요하다. 단순 “내일 오전 7시 알람 맞춰줘”는 알람 이름을 추가로 묻지 않고 중립적인 기본 이름 “알람”을 사용한다. 기상·복약 같은 목적을 추측하지 않는다.
두 개 날짜·시간을 포함한 입력은 명확한 시작~종료/기간 구문만 허용한다. 나머지는 첫 날짜를 골라 저장하지 않는다.
“다음 주 수요일”, “다음 달 31일”, 복수 일정·반복·종일 일정은 최초 범위 밖이다. 구체적인 월일/시각을 요청하고 주간 반복으로 근사하지 않는다.
기본 시간대는 설정에 표시한 Asia/Seoul을 사용한다. 기기 시간대가 다르면 변환 결과와 기준을 보여주고 조용히 다른 instant로 변경하지 않는다.
DST 간격/중복이 있는 선택 시간대를 후속 지원한다면 유효 offset을 검사한다. 존재하지 않거나 둘로 해석되는 시각을 자동 보정하지 않는다.

명시적인 생성 명령 동사와 대상이 있어야 mutation이다. 일정/알람 경로를 기존 “기억해줘” 처리보다 먼저 구별해 로컬 부탁으로 잘못 저장하지 않는다.
“10월 17일 3시 약속 있어?”, “캘린더에 뭐 저장돼 있어?”, “알람 맞췄어?”는 생성하지 않는다.
“저장하지 마”, “등록 취소”, “‘일정 추가해줘’라는 문장 설명”, “캘린더에 저장된 약속 알려줘”도 생성하지 않는다.
일반 조회·삭제·수정·외부 저장 완료 여부 질문을 지원하지 못하면 가능한 범위를 말한다. 생성 명령으로 fallback하지 않는다.
본문 공지·OCR 내용은 이 명령 파서의 실행 입력이 아니다. 엄마가 직접 보낸 현재 요청만 실행 권한을 갖는다.

## 6. 일정 시간과 최초 기본값

이 절의 종료 시각·기본 기간은 캘린더 일정에만 적용한다. 알람은 한 시점의 요청이므로 23:30 알람에 1시간 종료나 자정 경계 확인을 요구하지 않는다. 알람 요청에 별도 종료·지속 기간이 명시된 경우 지원하지 않는 부분을 조용히 버리지 않고 확인한다.

처음 저장 위치를 정할 때 “끝나는 시간이 없으면 1시간, 별도 알림 없음”을 기본 설정으로 함께 보이고 변경할 수 있게 한다.
기본값이 설정된 뒤 종료 없는 요청은 start+60분으로 만들며 응답에 시작~종료를 항상 표시한다. 60분은 원문에서 추출한 사실이 아니다.
명시된 종료 시각/기간은 기본값보다 우선한다. 종료≤시작이면 날짜를 넘기지 말고 확인한다.
명시 종료가 없는 23:30처럼 기본 기간이 자정을 넘기는 요청은 끝 날짜를 한 번 확인하고 저장한다. “당일 약속”을 다음 날까지 몰래 만들지 않는다.
지정된 지속 시간이 과도하거나 반복 요청이면 명확한 단일 시작~종료로 확인한다. 0.8 최대 기간은 24시간으로 제한한다.
캘린더 자체 알림과 모모 알림을 자동으로 둘 다 만들지 않는다. “알림도”가 없으면 별도 모모 예약·외부 알람 요청을 하지 않는다.
캘린더 앱/서버가 자체 기본 알림을 적용할 수 있으므로 readback에서 알림을 확인하고 모모가 추가한 알림과 구분한다.

## 7. CalendarProvider 직접 저장과 증거

Android [Calendar Provider](https://developer.android.com/identity/providers/calendar-provider)의 Events 삽입과 query readback을 사용한다. READ_CALENDAR/WRITE_CALENDAR는 첫 직접 저장 요청에 필요한 시점에만 요청한다.
일정 제목·시작/종료·시간대·선택 calendar ID만 최소 필드로 쓴다. 불필요한 자녀 프로필·공지 원문을 설명란에 복사하지 않는다.
요청 UUID와 정규화 payload, 목적지, 상태를 로컬 암호화 실행 기록에 먼저 저장한다. double tap·Activity 회전·복귀는 같은 요청을 재사용한다.
insert 반환 URI에서 얻은 event ID를 기록하고 같은 ID를 query해 calendar ID·제목·시작/종료·시간대가 일치하는지 확인한다.
성공 문구: “개인 캘린더에 10월 17일 14:00~15:00 치과 약속을 저장했어요.”와 `일정 보기`·`방금 저장 취소`.
이 성공은 기기 CalendarProvider에 저장됨을 뜻한다. 계정 서버 동기화·다른 기기 반영까지 완료됐다고 말하지 않는다.
insert 실패면 저장 실패다. URI 반환 뒤 readback 실패/권한 철회면 “저장 여부 확인 중” 상태로 두고 조회 재시도만 한다.
insert 결과를 잃은 상태에서 새 insert를 자동 재시도하지 않는다. 결과 불명 요청을 별도 표시해 중복을 방지한다.
실행 중 프로세스가 종료되면 기록된 ID로 재조회한다. ID를 기록하기 전 중단된 경우 무조건 재삽입하지 않는다.
같은 텍스트라는 이유만으로 영구 중복 제거하지 않는다. 엄마가 별도로 명령한 새 요청과 동일 요청의 재전달을 구별한다.

## 8. Undo는 모모가 만든 일정에만

로컬 실행 기록의 성공 event ID·calendar ID·생성 payload snapshot이 있는 방금 생성 건만 취소 대상이다.
사용자 기존 일정·검색 결과의 유사 일정·외부 입력 화면에서 생성했을 수 있는 일정은 삭제하지 않는다.
삭제 직전 현재 event와 관련 알림/참석자 상태를 확인한다. 제목·시간·위치·설명·반복·참석자·알림 등이 외부에서 달라졌으면 자동 삭제하지 않고 일정 보기를 제공한다.
검증과 삭제 사이 변경을 방지하도록 provider가 지원하는 batch assertion/조건부 삭제를 사용한다. 변경 보호를 보장할 수 없으면 자동 undo 대신 원문 일정 화면을 연다.
삭제된 event ID는 성공 취소 상태로 처리하되 다른 ID를 찾아 대체 삭제하지 않는다. calendar 전체 삭제·계정 해제는 하지 않는다.
삭제 후 query로 부재를 확인하고 “방금 저장한 일정을 취소했어요”라고 답한다. query 실패면 취소 확인 불가로 표시한다.
권한 철회·계정 삭제·동의 철회 뒤에 늦은 callback이 외부 쓰기/삭제를 시작하지 못하게 실행 generation을 검증한다.

## 9. 외부 캘린더 입력 화면 fallback

provider 미노출·권한 거절·외부 앱 직접 입력 선호 시 `ACTION_INSERT`로 제목·시작·종료를 채워 선택 앱에 전달한다.
앱 전환 전에 해석한 날짜와 대상 앱이 보이고, 반환 후에는 “일정 입력 화면을 열었어요. 저장은 캘린더 앱에서 마쳐주세요”라고 답한다.
Activity의 결과 코드·앱 복귀·화면 열기 성공만으로 저장 완료를 확정하지 않는다. callback 없는 앱은 `EXTERNAL_UI_OPENED` 상태로 남긴다.
일반 intent는 특정 캘린더 계정까지 강제 선택하는 계약이 아니다. 외부 앱에서 선택한 계정과 모모의 provider 기본 계정을 동일시하지 않는다.
handler 없음·실행 오류면 payload를 보존해 다음 목적지를 고를 수 있게 한다. 실패 후 다른 앱으로 연속 실행하지 않는다.
외부 입력 요청에는 모모 자동 undo를 제공하지 않는다. 실제 event ID가 없으므로 삭제 권한이 없다.

## 10. 선호 알람 앱으로 요청할 수 있는 범위

Android [Common intents](https://developer.android.com/guide/components/intents-common)의 `AlarmClock.ACTION_SET_ALARM`은 시·분·요일 반복 계약이다. 임의의 연월일을 보낼 표준 필드가 없다.
외부 알람 handoff에는 시·분·짧은 label을 보내며 요일 반복은 설정하지 않는다.
엄마의 명시적 생성 명령, 한 번 선택한 실제 `ACTION_SET_ALARM` handler, 다음 발생일 일치가 모두 충족되면 `EXTRA_SKIP_UI=true`로 자동 설정을 요청한다. 같은 목적지에 매번 저장 확인을 반복하지 않는다.
공식 계약은 true인 경우 수신 앱이 확인 UI를 생략하고 알람을 설정하도록 규정한다. 이는 정식 intent 옵션이며 접근성 자동 클릭이나 보안 확인 우회가 아니다.
사용자가 수동 확인을 선호하거나 해당 앱의 skip 지원 불가가 확인된 경우에는 `EXTRA_SKIP_UI=false`로 설정 화면을 요청한다. handler 자체가 없으면 false로도 보내지 않는다.
요청한 절대 날짜/시각과 현재 시간대에서 다음에 오는 그 시·분이 정확히 같을 때만 외부 앱 경로를 제시한다.
예: 오늘 18시에 내일 오전 7시 요청은 next occurrence와 일치한다. 오늘 18시에 다음 달 17일 오전 7시 요청은 불일치다.
자정·시각 경과·앱 선택 지연을 고려해 launch 직전 재검사한다. 시·분으로 줄이면서 날짜를 내일로 바꾸지 않는다.
불일치면 “이 알람 앱의 공통 연결은 날짜를 지정할 수 없어요”와 `모모에서 이 날짜에 알리기` 또는 `캘린더에 저장`을 제공한다.
이는 목적지가 바뀌는 경우이므로 한 번 선택이 필요하다. 외부 요청을 조용히 로컬 예약으로 바꾸지 않는다.
true 요청이 예외 없이 전달되면 `REQUEST_DISPATCHED`로 기록하고 “선택한 앱에 07:00 알람 설정을 요청했어요”라고 답한다. `SAVED`로 승격하거나 실제 생성·다음 울림·알람 ID를 확인했다고 주장하지 않는다.
false 경로는 “선택한 앱에 07:00 알람 설정 화면을 열었어요”라고 답한다. 이 경우에도 완료 receipt나 자동 undo는 없다.
true 요청 전달 뒤 저장 확인이 없다는 이유로 false 요청이나 true 요청을 자동 재전송하지 않는다. 화면 복귀·회전·동일 요청 재실행에서도 중복 전달을 막는다.
표준 알람 앱의 임의 삭제·완료 receipt·모든 미리알림 앱의 CRUD는 지원한다고 말하지 않는다. 외부 알람 undo 버튼을 만들지 않는다.
지원하는 handler가 있는 사실과 올바른 날짜에 실제 생성되는 사실은 다르다. 휴대폰이 오프라인인 현재는 특정 Alarmy의 handler·skip 동작을 확인하지 못했으며 “설정 요청 전달 기능, 앱별 호환 미검증” 수준으로 표시한다.
추가 회귀는 true의 세 조건, 수동 선호/skip 미지원 false, handler 없음 실행 0건, 전달 후 거짓 `SAVED`·undo·자동 재전송 0건을 검증한다.

## 11. 모모의 특정 날짜 알림 유지

기존 TaskReminderScheduler의 절대 timestamp 예약을 재사용한다. 특정 날짜·시각을 로컬로 저장하고 readback한 경우만 “모모에 알림을 저장했어요”라고 답한다.
알림 권한·채널 상태·exact alarm 권한을 점검한다. exact 권한이 없으면 “지정 시각 무렵”이라고 표시하며 정확히 울림을 보장하지 않는다.
저장된 예약·시스템에 예약 요청됨·실제 알림 전달은 별개 결과다. 기기가 꺼져 있거나 권한이 사라졌을 때 전달 보장을 하지 않는다.
재부팅·시간 변경 후 이미 지난 날짜를 내년/다음 날로 변경하지 않는다. 놓친 예약은 경과 상태로 남기고 정기 브리핑에서 한 번 안내한다.
원문 요청과 달리 알림 예약이 실패하면 “부탁만 저장됨”을 명시하고 해결 경로를 제공한다. 성공 메시지를 먼저 보여주지 않는다.
모모 예약의 취소는 해당 task ID/occurrence/generation에 한정한다. 다른 브리핑 슬롯이나 외부 시계 앱 알람에는 영향을 주지 않는다.

## 12. GPT-5.5 구현 소유 범위와 순서

일정 연동과 알람 화면을 각각 GPT-5.5 담당자가 구현한다. 일정 담당자는 parser/calendar/ExternalAlarmGateway/AgentActivity/LocalAgentEngine/MainActivity/Manifest/버전을, 알람 담당자는 BriefingActivity/BriefingReminders/AlarmContent/TaskAlarmActivity/TaskReminderScheduler/AssistantTaskStore를 전담한다. 각자의 테스트도 같은 경계를 따른다. TaskStore의 기존 호출 계약은 유지한다. 두 작업의 소스 변경이 끝난 뒤 일정 담당자만 순차 빌드하며, 다른 작업의 0.7 수정·테스트를 되돌리지 않는다.

| 200% 글자·작은 화면·TalkBack | 주 제어 접근/문장 확인 가능, 버튼 의미·순서 일치 |

0.7 테스트와 새 parser/gateway/store/알림 회귀·lint·빌드를 통과해야 한다. resolver/provider fake 시험은 실제 앱 호환성 증명이 아니다.
휴대폰 연결 뒤 선택 캘린더의 실제 저장/조회/변경된 일정 undo 차단, 지원 시계 앱의 입력 화면/다음 울림, 잠금화면을 별도 검증한다.
화면 개선 평가는 같은 모모 과제에서 행동 이해 정확도·할 일 찾는 시간·소리 끄기/다시 알림 성공·실제 행동 완료와 잘못된 완료 0건을 목표로 기록한다. Alarmy 우월성 결론은 내리지 않는다.
실기기 검증 전 배포 보고는 구현·자동 검증 범위와 미검증 앱/권한/잠금 제약을 명시한다.
