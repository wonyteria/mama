# 나는 엄마다 — 엄마 개인 비서의 제품 방향

2026-09-13 · 최신 사용자 의도 반영 · 현재 APK 구현 범위와 구분하는 제품 기준

## 1. 서비스가 해야 하는 일

**엄마가 허용한 정보에서 가족에게 필요한 일을 발견하고, 가족의 상황과 선호를 기억해, 실행에 필요한 준비를 마친 뒤 우리 앱에서 알려주는 개인 비서.**

엄마는 최초 계정 연결·동의 후 평소에는 우리 앱에서 필요한 정보를 확인한다. 새 정보를 얻기 위해 매번 다른 앱을 열거나 링크를 복사·공유하는 습관을 요구하지 않는다. 원래 서비스의 결제·서명 등 최종 절차가 필요한 경우는 원문 수집과 분리하며, 사용자가 선택한 실행 단계에서만 연결한다.

## 2. 푸시와 원문에 대한 정확한 사실

- 푸시에 본문이 실려 있으면 그 범위는 읽을 수 있다. 푸시가 제목·‘새 공지’만 보내면 NotificationListenerService 자체가 없는 원문을 가져다주지는 않는다.
- 실제 S23에서는 합성 알림의 본문 수집을 확인했다. 실제 e알리미·하이클래스의 신규 푸시 본문은 아직 측정하지 못했다.
- 실제 e알리미 한 건에서는 개발자가 앱을 열어 확인한 **앱 제공 공지 링크 → HTML → PDF → 본문 텍스트** 경로가 성공했다.
- 이를 **푸시만으로 원문 자동 확보 성공**이라고 부르면 안 된다. 새 공지/원문 링크 자동 발견과 지속 연결은 아직 미검증이다.

근거: [실기기 검증](../mom-agent/device-tests/2026-09-13-results.md), [Android 알림 리스너](https://developer.android.com/reference/android/service/notification/NotificationListenerService).

## 3. 선택하는 수집 방향

```text
허용한 정보원에서 새 소식/요청 감지
                  ↓
앱별 원문 연결: 공식 API/피드 또는 허용된 웹 세션
                  ↓
원문/첨부를 확보하고 대상·날짜·의도·확실성 확인
                  ↓
가족의 기존 일정·미완료 업무·선호와 연결
                  ↓
할 일 / 준비물 / 구매 목록 / 변경 사항으로 정리
                  ↓
비교·추천·구매 링크 등 필요한 준비
                  ↓
엄마가 우리 앱에서 확인하고 선택
```

푸시는 새 소식을 알려주는 신호로 활용하며, 앱별 원문 연결이 내용을 책임진다. API/웹 연결로 확보할 수 없는 앱에 한해, 정해진 화면 읽기 자동화의 가능성과 안정성을 따로 검증한다. 다른 앱을 자동으로 열고 돌아다니는 동작을 모든 Source의 공통 해법으로 가정하지 않는다.

Android의 백그라운드 화면 실행 제한, 잠금 상태, 앱별 UI 변경, 접근성 API의 사용·배포 조건을 함께 본다. PC에서 ADB로 조작한 실험 성공은 일반 소비자 앱이 항상 같은 일을 할 수 있다는 증거가 아니다. [Android 화면 실행 제한](https://developer.android.com/guide/components/activities/secure-bal), [Google Play 접근성 정책](https://support.google.com/googleplay/android-developer/answer/10964491?hl=es).

## 4. 장보기 시나리오

예시 요청: ‘수요일까지 8절 스케치북 한 권이 필요해.’

1. 허용된 메시지 연동 또는 우리 앱의 음성/텍스트 입력으로 들어온 요청에서 필요 물품·규격·수량·필요 시점을 추출한다.
2. 누가 필요한지와 출처를 연결한다. ‘안 사도 됨’, ‘학교에서 제공함’, 취소된 요청은 구매 필요로 확정하지 않는다.
3. 기존 미완료 구매 목록과 중복을 확인하여 같은 요청을 여러 번 등록하지 않는다. 확인되지 않은 집 안 재고나 외부 구매 이력을 아는 척하지 않는다.
4. 기억된 선호 판매처에서 같은 상품/조건의 후보를 찾는다. 쿠팡 선호면 쿠팡, 네이버 선호면 네이버, 둘 다 선택했으면 둘 다 비교한다.
5. 상품가·배송비·수량·규격·도착 예정일·확인 가능한 할인 조건을 비교하고, 검증된 조건 안에서 추천한다.
6. 우리 앱에 추천 이유·비교 결과·가격 확인 시각·구매 링크를 준비한다. 구매는 사용자가 선택한다.

‘스케치북’처럼 규격이 없으면 제품을 임의로 확정하지 않는다. 기존 선호/명확한 맥락으로 해결되지 않는 중요한 조건만 확인한다. 특정 기한까지 도착하지 못하는 저가 상품을 최선으로 추천하지 않는다.

이 예시는 요구 동작이며 현재 가격 검색·가족 메시지·음성 입력이 구현됐다는 뜻이 아니다. 실제 지원 가능한 메시지 서비스와 상품 정보 접근 경로는 각각 검증해야 한다.

## 5. 개인화와 가격 비교 원칙

| 항목 | 제품 기준 |
|---|---|
| 선호 쇼핑몰 | 최초 선택 또는 우리 앱에서 사용자가 선택한 결과를 기억. 설치됐다는 이유로 자주 쓴다고 단정하지 않음 |
| 비교 범위 | 지원·선택된 판매처와 확인한 상품 후보 범위를 표시 |
| 같은 상품 | 모델/규격/옵션/수량을 맞춰 비교. 다른 규격의 낮은 표시 가격을 최저가로 추천하지 않음 |
| 총액 | 상품가+배송비-실제로 확인 가능한 할인. 확인 못 한 회원 할인·카드 조건을 임의 적용하지 않음 |
| 도착 조건 | 필요 날짜 안에 도착할 수 있는지 확인, 미확정이면 명시 |
| 최저가 표현 | ‘확인한 후보 중 조건에 맞는 최저 총액’으로 표현. 시장 전체의 절대 최저가를 보장하지 않음 |
| 최신성 | 가격 확인 시각·품절·옵션 변동을 표시하고 실행 시 재확인 가능한 링크 제공 |
| 실행 범위 | 목록·비교·링크 준비까지 자동화. 자동 결제/주문은 현재 요청 범위에 없음 |

## 6. 정보를 받는 조건

가족이 말한 모든 내용을 저절로 알 수 있다고 가정하지 않는다. 실제로 동의하고 연결된 정보원 또는 앱으로 전달된 요청만 처리한다. 수집이 안 되는 메시지 서비스를 전체 대화까지 읽는다고 약속하지 않는다.

가족 요청을 직접 말하는 기능은 사용자가 새로운 필요를 전달하는 선택 기능이다. 학교 공지마다 엄마가 다시 설명해야 한다는 뜻이 아니다. 이미 다른 서비스에 존재하는 공지의 반복 재입력은 계속 제외한다.

## 7. 개발 순서

1. **지금:** 실제 e알리미에서 최초 연결 후 새 공지와 원문을 자동 확보하는 경로 검증. 수집 앱의 실기기 설정/잔여 테스트 정리.
2. **첫 가치 경험:** 원문 근거에 따라 준비물·마감·변경을 정확하게 정리하고 우리 앱에서 확인·완료·미루기.
3. **같은 기반 확장:** 가족의 요청을 구매 필요로 이해하고, 개인 선호에 맞춘 비교·링크 준비. 실제 상품 정보 접근 가능성과 사용자 수고 감소를 검증.

기능을 늘리는 것보다 ‘필요 발견 → 맥락 이해 → 준비 완료’가 한 사례에서 끝까지 작동하는지가 먼저다. 학교 공지와 장보기는 이 공통 흐름을 사용하는 서로 다른 업무다.

## 8. 완료라고 부를 조건

- 엄마가 원래 공지를 열지 않았어도 필요한 원문을 확보한다.
- 단순 언급과 실제 행동 필요를 구분한다.
- 가족·규격·날짜·선호를 정확히 연결한다.
- 같은 일을 중복시키지 않고 변경/취소를 반영한다.
- 정보를 나열하는 데 그치지 않고, 엄마가 선택할 수 있는 준비된 결과를 제공한다.
- 데이터가 없거나 확인하지 못한 조건은 드러낸다.
- 가족 정보·세션·원문을 허용 범위 안에서 다루고 중단·삭제할 수 있다.

현재 G0 APK는 이 전체 개인 비서의 첫 수집 실험 도구이며, 위 기능이 모두 구현된 제품이 아니다.
